### `sequence_no_decoder_output` SIGSEGV — root cause (pre-existing TEST bug, fixed)

Reproduced on a pristine detached worktree at the base `ef2c7d85` (no GB/T change),
so it is pre-existing and unrelated to the GB/T increment. Detailed analysis
(ASan stack + guarded-repro isolation) shows it is **a test-diagnostic bug, not a
library decode defect**:

- Crash stack: `_platform_strlen` ← `std::ostream << (char const*)` ←
  `Catch::MessageBuilder::operator<<` ← `sequence_no_decoder_output.cc:390` (the `INFO`).
- Catch2's `INFO` macro (catch_amalgamated.hpp:4041) builds its message **eagerly**:
  `MessageBuilder(...) << log` runs `m_stream << err.message` at the INFO statement,
  i.e. `strlen(err.message)` on every iteration regardless of assertion outcome.
- The failing case "decoder latency may exceed the length of the repeated segment"
  expects 200 **successful** frames. On success `heif_error.message == nullptr`, so
  `strlen(NULL)` → SIGSEGV. (The sibling case at line 300 is safe only because it
  expects a real error with a non-null message.)
- **Proof the library is correct:** guarding only the INFO null-message
  (`err.message ? err.message : "(null)"`, no other change) makes the case pass all
  404 assertions — all 200 frames decode successfully with latency 24 > segment
  length 1. ASan/UBSan report no memory error. An earlier "UB" hypothesis was
  disproven by this guard-only isolation.

**Fix applied** (test-only, matches repo convention `error.message ? error.message : ""`
used in tmap_write.cc): guard the null message in both INFO sites
(tests/sequence_no_decoder_output.cc:300 and :390). No library/ABI change.
